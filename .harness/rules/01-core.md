# 核心行为规则

## 1. 任务分解原则

### 1.1 强制分解条件
以下情况**必须**将任务分解为子任务：
- 任务预计超过 30 分钟完成
- 涉及多个文件修改（>3 个文件）
- 需要同时修改 API 和数据库结构
- 涉及不熟悉的代码库区域

### 1.2 分解粒度标准
- **最小可交付单位**：每个子任务应产生可独立验证的结果
- **最大复杂度**：单个任务不超过 200 行代码变更
- **依赖声明**：明确标注子任务间的依赖关系

## 2. 自主决策边界

### 2.1 完全自主（无需确认）
- 代码格式调整（换行、空格、import 排序）
- 文档字符串和注释添加
- 不影响行为的代码重构（变量重命名等）
- 测试用例的补充（不改变原有用例）

### 2.2 需要确认（人类介入）
- 修改公共 API 签名（函数名、参数、返回值）
- 删除代码文件或大量代码块（>50 行）
- 引入新的依赖包
- 修改数据库 schema
- 涉及安全相关的改动（认证、授权、加密）
- 可能影响性能的改动（算法复杂度、循环嵌套）

### 2.3 禁止自主执行
- 提交到生产分支（main/master）
- 执行破坏性命令（`rm -rf`, `DROP TABLE` 等）
- 访问/修改敏感配置文件（密码、密钥、token）
- 执行网络请求到外部 API（除非配置允许）
- 创建或修改 CI/CD 管道配置

## 3. 执行流程标准

### 3.1 阶段检查点
每个任务必须通过以下检查点：

#### Phase 1: Analyze（分析）
- [ ] 理解任务目标和范围
- [ ] 识别相关代码区域
- [ ] 评估影响范围
- [ ] 分解子任务（如需要）
- **输出**: `task-analysis.md`

#### Phase 2: Plan（规划）
- [ ] 制定执行计划
- [ ] 识别依赖和风险
- [ ] 确定验证方法
- [ ] 标记需人工确认的点
- **输出**: `execution-plan.md`

#### Phase 3: Execute（执行）
- [ ] 按顺序执行子任务
- [ ] 每个子任务后运行验证
- [ ] 遇到阻塞立即暂停并报告
- [ ] 保留中间状态便于回滚
- **输出**: 代码变更、日志

#### Phase 4: Review（审查）
- [ ] 代码自审（对照编码规范）
- [ ] 运行自动化检查
- [ ] 生成变更摘要
- [ ] 准备审查报告
- **输出**: `review-report.md`

#### Phase 5: Finalize（完成）
- [ ] 整理提交信息
- [ ] 清理临时文件
- [ ] 更新文档（如需要）
- [ ] 任务总结
- **输出**: `task-summary.md`

### 3.2 中断与恢复
- **中断触发**：人类介入、遇到未知错误、资源不足
- **状态保存**：当前阶段、已完成的子任务、关键变量
- **恢复流程**：读取状态 → 验证环境 → 继续执行/重新规划

## 4. 质量保证要求

### 4.1 代码质量标准
- 每个函数/类必须有文档字符串
- 复杂逻辑必须有注释说明 "为什么"
- 新代码必须通过类型检查（mypy）
- 代码风格必须符合项目规范（ruff/black）
- 新增代码必须伴随测试（单元/集成）

### 4.2 文档要求
- 每个 PR 必须有清晰的描述
- 复杂功能必须有使用文档
- API 变更必须更新 API 文档
- 架构决策必须记录 ADR

## 5. 合规与伦理

### 5.1 数据处理
- 不得记录或传输敏感数据（密码、密钥、PII）
- 日志中必须脱敏处理
- 遵守项目的数据处理政策

### 5.2 知识产权
- 遵守开源许可证要求
- 不复制未经授权的代码
- 正确标注引用来源

### 5.3 透明度
- 清晰说明 AI 参与的工作
- 保留决策记录便于审计
- 主动披露已知限制
